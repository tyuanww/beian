## 发版流程

1. Mac 上开分支开发；一个提交一个目的，`type(scope): 描述`；不 `git add -A`。
2. 用户明确说 `/ship` 才开 PR。CI 两个 job：`quality`（ubuntu，完整 L0）和 `windows-powershell-contract`（GitHub 托管的 windows-2022）。两个都绿才合并。
3. squash 合并到 `main` 会自动触发 `hangzhou-release`（杭州 self-hosted runner 跑 `release.ps1`）。等它变绿，再等约 20 秒，确认公网 `https://www.jianghua.site/api/health` 的 `version` 等于刚合入的 `VERSION`，才能说「已上线」。
4. 版本号同时改 `VERSION`、`CHANGELOG.md`、`apps/web/server/src/index.ts` 里的 `VERSION` 常量。

## 禁区

- 不登录、不操作杭州生产机；发版只走 runner。不重跑或恢复 runner，不改 DNS，不发布飞书版本，不买云，不开公网端口。
- 不读、不打印密钥；不提交 `.env*`、`apps/web/backend/data/` 运行时文件、稿件、`.claude/`。
- 发消息（包括测试消息）和删除重要数据都要有明确授权。
- 不改 `apps/web/backend/data/runtime/`。

## 坑

- Windows 上改名覆盖一个正被打开的文件会报 EPERM；删除被打开的文件能成功，但句柄没关之前文件还列在目录里。替换文件要写新文件名，不要原地覆盖。测试里打开的句柄一定要关。
- Windows checkout 是 CRLF，读源码做静态断言前先把 `\r\n` 换成 `\n`。
- CI `quality` 偶发：`release-http.test.ts` 下载计数、`test_packaging_render_generation.py` 的 `resource_accounting_unavailable`。单独跑都过，先重跑失败 job 再判断。
- Node 20 下 `apps/web/ui` 的 `npm test` 不展开通配符；全新环境构建缺 `@rollup/rollup-linux-x64-gnu`，要单独装。
- Mac 在后台长跑的 shell 会被断开；全套检查分段在前台跑。
- 合 `main` 等于发版到杭州，合并授权必须包括这一点。
